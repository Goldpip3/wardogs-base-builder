# Build config

Two small files that are not data but **switches**: they change what the build emits.
`data/community.json` carries `voteApi`; `data/ads.json` carries `publisherId` and slots.

## Why this shape

Both default to empty, and empty means the feature does not ship at all rather than shipping
broken. With no `voteApi` there is no sign-in, no account page, no moderation page, and the
planner has no cloud save. With no `publisherId` there is no ad script, no slot, no reserved
space, and `docs/ads.txt` is actively deleted, because an ads.txt naming nobody is worse
than none.

`publisherId` is in its own file for one specific reason: the buildables catalog is inlined
whole into the downloadable planner, so anything in it travels inside the file people keep.
An advertising identity has no business in a file people keep on a disk. `tools/check-build.js`
asserts the *downloadable* planner carries no publisher id, no ad markup and no unreplaced
placeholder, which is what stops that being re-merged by accident. The hosted planner does
carry one ad, and is allowed exactly one outside origin.

## Shape

- `community.json`: `voteApi` (worker origin), `designs[]` (slug + share code)
- `ads.json`: `publisherId`, `slots{}`

Three slots, and they are not all placed the same way, which is the thing to know before
adding a fourth.

`leaderboard` and `inArticle` are placed by `adSlot()` in `tools/site/context.js` and each
needs a matching entry in its `AD_FORMATS` table, which carries the markup that unit type
wants: the leaderboard is a responsive display unit, the in-article one is AdSense's fluid
format. `adSlot()` returns an empty string for a name it does not know, so a slot with an id
and no format costs nothing and says nothing.

`planner` is different. The planner is not generated by that file, so `build.ps1` injects it
directly, into the hosted copy only, at the foot of the right panel. Adding it to
`AD_FORMATS` would do nothing.

A check asserts every id with a value reaches a built page, which is what catches a slot
placed nowhere in either scheme.

Citations: `build.ps1:44` reads `voteApi`; injected at `build.ps1:61` and only there.

## Connected to

- **owns:** whether the hosted planner can save online; whether ads exist
- **joins:** [vote-worker](../service/vote-worker.md), [planner-app](../planner/planner-app.md)
- **looks-like-but-is-not:** [buildables-catalog](buildables-catalog.md). That is data the
  product is about; this is configuration the build reads.

## If you change this

- **Hits:** setting `voteApi` turns on `/account/` and `/moderate/` (both `noindex`), the
  header sign-in on every page, and cloud save in the hosted planner only. Setting
  `publisherId` writes `docs/ads.txt` and adds the ad script to the content pages and, if
  the `planner` slot also has an id, to the hosted planner.
- **Does not hit:** `WardogsBaseBuilder.html`. The downloadable build gets an empty string
  for the API, and empty strings for both ad placeholders, always. Three checks enforce it:
  no publisher id, no ad markup, nothing external loaded. Adding designs to
  `community.json` also does not touch the worker, which stores votes separately.

## Surfaces

| Surface | Role |

| `tools/check-build.js` | asserts the offline build stayed clean |
